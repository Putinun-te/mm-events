# MM Events on AWS (EKS)

Terraform for the AWS side and the shared Helm chart [`deploy/helm/mm-events`](../../helm/mm-events)
for the app: the Spring Boot API and the nginx-served Nuxt frontend run on EKS behind an
ALB created by the AWS Load Balancer Controller, MySQL 8 runs on RDS, and the secrets live
in Secrets Manager and reach the pods through the External Secrets Operator with IRSA.

![AWS architecture](../../diagrams/aws.png)

| Piece | Service | Notes |
|---|---|---|
| Network | VPC, 2 public + 2 private subnets in 2 AZs | One NAT gateway; subnets tagged for the Load Balancer Controller |
| Kubernetes | EKS, API authentication mode, control-plane logs to CloudWatch | Kubernetes version: EKS default unless `kubernetes_version` is set |
| Nodes | Managed node group, 2 x `t3.medium` (1-3), AL2023, private subnets | Add-ons: VPC CNI, kube-proxy, CoreDNS, metrics-server (for the HPA) |
| Images | ECR `mm-events-backend`, `mm-events-frontend` | Scan on push, last 10 images kept |
| Ingress | ALB from the chart's Ingress (`alb` class, target type `ip`) | AWS Load Balancer Controller, IRSA role with the controller's published policy |
| Database | RDS MySQL 8.0, `db.t4g.micro`, 20 GiB gp3, private subnets | Encrypted, TLS required, only the cluster security group may connect |
| Secrets | Secrets Manager | DB password created and managed by RDS; JWT secret generated by Terraform |
| Secret delivery | External Secrets Operator, `SecretStore` with IRSA | The backend's service account role may read exactly the two secrets |

**Frontend on the ingress, not S3 + CloudFront.** The static Nuxt build is served by an
nginx pod behind the same ALB as the API: one origin, so no CORS and no mixed content
without a domain or certificate, the same chart works on all three clouds, and the image is
the repository's existing `main_frontend/concert1/Dockerfile`. The trade-off is no CDN; for
real traffic, put CloudFront in front of the ALB or move the static files to S3 + CloudFront.

**No secrets in Terraform state.** RDS generates and stores the master password
(`manage_master_user_password`); the JWT secret comes from an ephemeral `random_password`
written through the write-only `secret_string_wo`. The `helm_values` output contains only
names and ARNs.

## Prerequisites

- An AWS account you own and credentials for it (`aws configure` or `AWS_PROFILE`) with
  rights to create VPC, EKS, EC2, ECR, RDS, IAM, Secrets Manager and CloudWatch resources.
- Terraform 1.11+, AWS CLI v2, `kubectl`, Helm 3, Docker.

## Deploy

Commands start in `deploy/terraform/aws`.

```bash
ROOT=$(git rev-parse --show-toplevel)
CHART=$ROOT/deploy/helm/mm-events
TAG=$(git rev-parse --short HEAD)
```

**1. Infrastructure** (about 20 minutes; EKS and RDS are the slow parts):

```bash
cp terraform.tfvars.example terraform.tfvars   # optional; set cluster_endpoint_public_access_cidrs
terraform init
terraform plan -out tfplan
terraform apply tfplan
```

**2. kubeconfig:**

```bash
$(terraform output -raw kubeconfig_command)
kubectl get nodes
```

**3. Cluster add-ons:** the AWS Load Balancer Controller and the External Secrets Operator.

```bash
helm repo add eks https://aws.github.io/eks-charts
helm repo add external-secrets https://charts.external-secrets.io
helm repo update

helm upgrade --install aws-load-balancer-controller eks/aws-load-balancer-controller \
  --namespace kube-system \
  --set clusterName="$(terraform output -raw cluster_name)" \
  --set region=ap-southeast-1 \
  --set vpcId="$(terraform output -raw vpc_id)" \
  --set serviceAccount.name=aws-load-balancer-controller \
  --set serviceAccount.annotations."eks\.amazonaws\.com/role-arn"="$(terraform output -raw lb_controller_role_arn)" \
  --wait

helm upgrade --install external-secrets external-secrets/external-secrets \
  --namespace external-secrets --create-namespace --wait
```

**4. Backend image:**

```bash
BACKEND=$(terraform output -raw ecr_backend_url)
aws ecr get-login-password | docker login --username AWS --password-stdin "${BACKEND%%/*}"
docker build --platform linux/amd64 -t "$BACKEND:$TAG" "$ROOT/main_backend"
docker push "$BACKEND:$TAG"
```

**5. Install the chart without the frontend**, so the ALB and its hostname exist:

```bash
terraform output -raw helm_values > mm-events-values.yaml   # git-ignored; names and ARNs only

helm upgrade --install mm-events "$CHART" \
  --namespace mm-events --create-namespace \
  -f "$CHART/values-aws.yaml" -f mm-events-values.yaml \
  --set backend.image.tag="$TAG" --set frontend.enabled=false

kubectl -n mm-events get externalsecret,pods      # SecretSynced, then pods Ready
SITE=http://$(kubectl -n mm-events get ingress mm-events -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
curl "$SITE/actuator/health"                       # {"status":"UP"} once the targets are healthy
```

**6. Frontend image with that URL, then enable it:**

```bash
FRONTEND=$(terraform output -raw ecr_frontend_url)
docker build --platform linux/amd64 --build-arg NUXT_PUBLIC_BACKEND_BASE_URL="$SITE" \
  -t "$FRONTEND:$TAG" "$ROOT/main_frontend/concert1"
docker push "$FRONTEND:$TAG"

helm upgrade mm-events "$CHART" --namespace mm-events \
  -f "$CHART/values-aws.yaml" -f mm-events-values.yaml \
  --set backend.image.tag="$TAG" --set frontend.image.tag="$TAG" --set publicUrl="$SITE"
```

Open `$SITE`. Flyway creates the schema on the backend's first start.

**HTTPS** needs a domain: request an ACM certificate for it, add
`alb.ingress.kubernetes.io/certificate-arn` and `listen-ports: '[{"HTTP":80},{"HTTPS":443}]'`
(plus `ssl-redirect: "443"`) to the Ingress annotations, set `ingress.host`, point the
domain at the ALB, and rebuild the frontend with the `https://` URL.

## Day-to-day

- **New version:** build and push both images with a new tag, then `helm upgrade` with that
  tag. The rolling update keeps at least one backend pod serving (PDB `minAvailable: 1`).
- **Logs:** `kubectl -n mm-events logs deploy/mm-events-backend -f`. Control-plane logs are
  in CloudWatch under `/aws/eks/mm-events/cluster`.
- **Rotate the JWT secret:** bump `secret_version`, `terraform apply`, then
  `kubectl -n mm-events annotate externalsecret mm-events-backend force-sync=$(date +%s) --overwrite`
  and `kubectl -n mm-events rollout restart deploy/mm-events-backend`. Existing logins end.

## Rough monthly cost

On-demand prices in `ap-southeast-1`, two nodes all month, little traffic. Check the
[AWS Pricing Calculator](https://calculator.aws/) before you deploy.

| Item | USD / month |
|---|---|
| EKS control plane (USD 0.10/hour) | ~73 |
| 2 x `t3.medium` nodes + 2 x 30 GiB gp3 | ~83 |
| NAT gateway (hourly, before data) | ~43 |
| Application Load Balancer | ~20 |
| RDS `db.t4g.micro` + 20 GiB gp3 | ~22 |
| Public IPv4 addresses (NAT, ALB) | ~11 |
| Secrets Manager, ECR, CloudWatch | ~4 |
| **Total** | **~255** |

The control plane, NAT gateway and ALB charge even when idle. Destroy the stack when you
are not using it.

## Destroy

Delete what Kubernetes created first, otherwise the ALB and its security groups (made by
the controller, not by Terraform) keep the VPC from being deleted:

```bash
helm uninstall mm-events --namespace mm-events
kubectl -n mm-events get ingress                  # wait until it is gone
helm uninstall aws-load-balancer-controller --namespace kube-system
helm uninstall external-secrets --namespace external-secrets
terraform destroy
```

This deletes the database **without a final snapshot** (the default `deletion_protection =
false`) and the JWT secret without a recovery window. Set `deletion_protection = true`
before you keep real data.

## Limits

- Photo uploads (`/api/upload`) need an S3 bucket and permissions that are not part of this
  setup, as in the Railway demo.
- The login rate limit is kept in memory per pod, so each backend replica counts separately.
- `cluster_endpoint_public_access_cidrs` defaults to everywhere; narrow it to your IP.
